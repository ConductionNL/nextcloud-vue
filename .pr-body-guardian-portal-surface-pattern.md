## Scope

Every corpus competitor examined in learniq round 1 (including both open-source ones) ships a distinct parent/guardian-facing surface; learniq and portaliq currently build guardian surfaces ad hoc, per app, with no shared component (`market-intelligence/learniq/tier-b-and-sibling.md` section 3, the M3(b) design-system request this round surfaced). This adds `CnGuardianHome`: a layout-only guardian/parent portal shell (children switcher, feed / agenda / consent-settings sections, a "report absence" entry point), composed entirely from existing library primitives (`NcCheckboxRadioSwitch`, `CnTabs`/`CnTab`, `NcButton`, `NcEmptyContent`). No new dependency.

The component owns only the shell. It fetches nothing and knows nothing about OpenRegister or any app's data model — `children` is plain data, and the feed/agenda/consent sections are scoped slots (`{ child }`) a host app fills with its own data-bound widgets. `activeChildId` is `v-model`-bindable and self-defaults to the first child when unset or stale. This ships ahead of its first consumer, matching how the design-system request itself is framed (the shared primitive, not a per-app build) — learniq's `portal-contribution-guardian-audiences` and portaliq's `portal-parent` are the intended first adopters.
