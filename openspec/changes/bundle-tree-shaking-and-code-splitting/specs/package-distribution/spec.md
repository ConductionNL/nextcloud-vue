# Package Distribution — Spec

## Purpose

Specifies the bundle-shape contract of the `@conduction/nextcloud-vue` npm package: how the
package is built, what `sideEffects` guarantee it makes to consumer bundlers, and which parts of
the library are eligible for lazy-loading. This capability governs `rollup.config.js`,
`package.json`'s `main`/`module`/`sideEffects` fields, and the built `dist/` output — it does not
govern any individual component's runtime behavior.

**Files**: `rollup.config.js`, `package.json`, `dist/` (generated), `src/utils/validateManifest.js`

**Cross-references**: [composables](../../../specs/composables/spec.md) (for `useAppManifest`'s
consumption of the async validator)

---

## ADDED Requirements

### Requirement: ESM output MUST be chunked, not inlined

The Rollup build's ES module output (`package.json`'s `"module"` entry point) MUST emit multiple
chunk files reflecting the library's internal module graph (e.g. via `output.dir` +
`preserveModules`), rather than a single inlined file. `inlineDynamicImports` MUST NOT be set on
the ESM output. The CJS output (`"main"`) MAY remain a single inlined file.

#### Scenario: A consumer importing one component does not receive the whole library

- GIVEN a consumer app imports only `{ CnStatusBadge }` from `@conduction/nextcloud-vue`
- AND the consumer's bundler performs standard ES module tree-shaking
- WHEN the consumer's production bundle is built
- THEN the resulting bundle MUST NOT include the compiled v2 manifest validator, CodeMirror,
  Leaflet, or any component the consumer never imported, transitively or otherwise

#### Scenario: Legitimate internal dynamic imports remain lazy chunks

- GIVEN `src/components/CnChartWidget/CnChartWidget.vue` dynamically imports `@nextcloud/axios`
  and `@nextcloud/router` inside a method body
- WHEN the library is built
- THEN those dynamic imports MUST NOT be inlined into the entry chunk

### Requirement: `sideEffects` MUST be a precise allowlist, not `true`

`package.json`'s `sideEffects` field MUST enumerate the specific files that have genuine
module-scope side effects (CSS entry points, the integration-registry's global install code).
It MUST NOT be the boolean `true`, which disables `usedExports`-based dead-code elimination for
the entire package in every consumer's bundler.

#### Scenario: Consumer bundler eliminates an unused component module

- GIVEN a component module (e.g. `src/components/CnIconBrowser/CnIconBrowser.vue`) has no
  module-scope side effects and is not imported by a consumer
- WHEN that consumer's bundler runs `usedExports` + `sideEffects`-based elimination
- THEN the unused component's module MUST be eligible for removal from the consumer's bundle

### Requirement: The compiled v2 manifest validator MUST be lazy-loaded

`src/utils/validateManifestV2.compiled.js` (the Ajv-standalone-compiled v2 schema validator, generated by `scripts/build-validators.js` per ADR-036) MUST NOT be statically imported from
`src/index.js`'s module graph at the top level. It MUST be reachable only via a dynamic
`import()` invoked at the point validation actually runs, so consumers that never call
`validateManifest`/`validateManifestV2` (directly or via `useAppManifest`) never load it.

#### Scenario: An app that never validates a manifest never loads the compiled validator

- GIVEN a consumer app renders zero manifest-driven pages and never calls `useAppManifest` with
  `validate: true`, nor calls `validateManifest`/`validateManifestV2` directly
- WHEN that consumer's production bundle is built and executed
- THEN the compiled v2 validator chunk MUST NOT be present in the consumer's initial bundle
  AND MUST NOT be fetched at runtime

#### Scenario: `useAppManifest`'s backend-merge branch still validates before publishing

- GIVEN `useAppManifest(appId, bundledManifest)` is called (legacy fetch-and-merge signature)
- WHEN the backend merge and sentinel resolution complete
- THEN the resolved manifest MUST still be validated (via the lazily-loaded validator) before
  `manifest.value` is updated, preserving the existing "never publish an invalid resolved
  manifest" guarantee

### Requirement: No unused dependencies are declared

`package.json` `dependencies` MUST NOT list a package that has zero import sites anywhere in
`src/`.

#### Scenario: `lodash` is removed

- GIVEN a repo-wide grep of `src/` for `lodash` import syntax
- WHEN the grep returns zero matches
- THEN `lodash` MUST NOT appear in `package.json`'s `dependencies`
