## Why

Every Conduction app that depends on `@conduction/nextcloud-vue` (OpenRegister, OpenCatalogi,
Procest, Pipelinq, MyDash, decidesk, docudesk, larpingapp, softwarecatalog, and any app that
imports the barrel) ships the library's **entire** `dist/nextcloud-vue.esm.js` — a single
monolithic file — verified on disk at **9,919,240 bytes (9.9MB)** (`dist/nextcloud-vue.esm.js`,
built 2026-07-03). There is no tree-shaking and no code-splitting: an app that imports only
`CnStatusBadge` bundles the same 9.9MB as an app that imports every component, composable, and
store the library exports.

Three compounding root causes, each verified against `HEAD`:

1. **`rollup.config.js:60,66` — `inlineDynamicImports: true`.** This Rollup output option
   forcibly inlines every module (including any future `import()` dynamic import) into the single
   output file. It makes per-export code-splitting structurally impossible regardless of any
   other fix — Rollup cannot chunk what it is told to inline.
2. **`package.json:22` — `"sideEffects": true`.** This tells every consumer's bundler (webpack,
   Vite, esbuild) that the entire package may execute side effects on import, which disables
   `usedExports`-based module elimination for the package. Even if the library shipped
   multiple ES modules, consumer bundlers could not safely drop the ones a given app never
   references.
3. **A 266KB compiled validator is unconditionally reachable from the entry point.**
   `src/index.js:283` statically exports `validateManifest, validateManifestV2` from
   `src/utils/validateManifest.js`, which at `src/utils/validateManifest.js:8` unconditionally
   imports `./validateManifestV2.compiled.js` — a build-time Ajv-standalone-compiled module
   measured at **266,380 bytes** (`src/utils/validateManifestV2.compiled.js`, generated by
   `scripts/build-validators.js` per ADR-036, to avoid Ajv's `new Function()` JIT under
   Nextcloud's CSP). Every app pays this cost even if it never calls `validateManifest`,
   never uses the v2 manifest schema, or renders zero manifest-driven pages.

A fourth, smaller finding: **`lodash` (`package.json` dependency, `^4.17.21`) has zero imports
anywhere in `src/`** (`grep -rn "lodash" src` returns no matches) — it is dead weight bundled into
every app for no reason.

Per CLAUDE.md, `apexcharts`/`vue-apexcharts` are *intentionally* bundled here (apps consume charts
via nc-vue, not their own dependency) — that decision is out of scope for this change and is not
touched.

## What Changes

- **Remove `inlineDynamicImports: true`** from both Rollup outputs in `rollup.config.js` and
  switch to `output.dir` + `format: 'es'` with Rollup's automatic chunking (`preserveModules` or
  manualChunks) for the ESM build, so components/composables/utilities that aren't imported by
  a consumer aren't pulled into that consumer's build graph. The CJS output (`format: 'cjs'`)
  keeps single-file inlining since CJS consumers can't chunk-split anyway — only the ESM output
  (the one bundlers tree-shake) changes shape.
- **Change `package.json`'s `sideEffects`** from `true` to an explicit array covering only the
  files that truly have module-scope side effects (`./css/index.css`, the integration-registry
  installer, any `window.OCA` bootstrap code) — everything else becomes `sideEffects: false`
  eligible for `usedExports` elimination in consumer builds.
- **Make the 266KB compiled v2 manifest validator dynamically imported** instead of a static
  top-level import in `src/utils/validateManifest.js`, so it only enters a consumer's bundle
  graph (and, at runtime, only downloads) when `validateManifest`/`validateManifestV2` is
  actually invoked. `useAppManifest`'s two call sites (`loadFromBackend`'s async IIFE and
  `loadInMemory`'s opt-in `validate: true` branch) already tolerate asynchronous resolution
  timing — see design.md for the exact behavior-preservation argument.
- **Remove the unused `lodash` dependency** from `package.json`.
- Rebuild `dist/` and diff the new bundle size per-export to confirm the fix actually shrinks a
  representative consumer's build (a minimal "import one component" smoke build).

## Impact

- **Affected specs**: new capability `package-distribution` (this change creates it — there is no
  existing capability spec for build/bundle-shape concerns).
- **Affected code**: `rollup.config.js`, `package.json`, `src/utils/validateManifest.js`,
  `src/composables/useAppManifest.js` (await the dynamic import), `dist/*` (regenerated).
- **Affected consumers**: all apps that depend on `@conduction/nextcloud-vue` — this is a
  bundle-size-only change; no public prop/event/slot/composable signature changes, so it does not
  require consumer-side code changes. `useAppManifest`'s external return shape
  (`{ manifest, isLoading, validationErrors, unresolvedSentinels, orphanedDeltaPaths }`) is
  unchanged; only the internal timing of when `validationErrors` first populates shifts by one
  microtask/chunk-load, which is already async in both call sites.
- **Backward compatibility**: no breaking changes to the public API. `main`/`module`/`types`
  entry points in `package.json` are unchanged; only the internal file layout of `dist/module/`
  changes shape (from one file to a directory of chunks) if the ESM output moves to `output.dir`.
  Consumers importing via the package name (`@conduction/nextcloud-vue`) are unaffected; anyone
  deep-importing `dist/nextcloud-vue.esm.js` by exact path (undocumented, ADR-004 says always
  import via the barrel) would need to update — grep across the fleet found no such deep imports.
